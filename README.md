# vrpspdtw-gpu-data

Data generated by **CoPTS-VRP**, a cooperative portfolio tabu search that runs on a graphics processing unit (GPU), for the
**vehicle routing problem with simultaneous pickup and delivery and time windows (VRPSPDTW)**.

This repository holds every run of the computational study of the manuscript *Cooperative parallel tabu search on a
graphics processing unit for vehicle routing with simultaneous pickup and delivery and time windows* (Jose Garcia,
Pontificia Universidad Católica de Valparaíso), including the verified solutions that are below every published value. The code is kept in a separate repository.

> **Resumen en español.** Este repositorio contiene todos los datos generados por CoPTS-VRP en el estudio computacional
> del manuscrito: una fila por ejecución en los ficheros `campaign_<tag>.csv`, la salida completa de cada ejecución
> (parámetros, rutas y traza por época) en `copts/` y `gma/`, las 17 soluciones verificadas que quedan por debajo de todo lo publicado en `new_best/`, el diagnóstico de reparación y los registros de las campañas. La tabla de
> campañas de más abajo indica qué ficheros corresponden a cada tabla y figura del artículo.

## Contents

| Path | Content |
|---|---|
| `campaign_<tag>.csv` | One row per run of the campaign `<tag>` (columns below). |
| `copts/` | Output of every CoPTS-VRP run: `<Instance>_copts_s<seed>_<timestamp>[_<tag>].json` with the parameters, the best solution and the per-epoch trace, and the matching `.sol.txt` with the routes. |
| `gma/` | The same for the batched memetic baseline (BMA). |
| `new_best/` | The 17 solutions of the final campaigns that are below every value published by MA-FIRD, MA-N, MA-E, MA-NTGA, MA-ETGA and DBLS-SP (16 JD instances and Rdp104), named `<instance>_M<vehicles>_total<cost>.txt`. |
| `repair_diag.json` | Repair diagnostic after the removal of the shortest route (RCdp101, 5 seeds). |
| `logs/` | Console logs of the campaigns and of the queues that chained them. |

The repository contains only results produced by our runs. Instances, reference solutions of other methods and code are
not included.

## Benchmarks and objective

* **Wang–Chen (WC):** 65 instances, 9 small ones with 10, 25 or 50 customers and 56 medium ones with 100 customers.
  Solutions are compared lexicographically by number of vehicles `M` and distance `D`. As in the literature, the weighted
  cost `total = 2000 M + D` is used to report gaps.
* **JD:** 20 instances with 200, 400, 600, 800 and 1000 customers and asymmetric cost and time matrices. The objective is
  the weighted cost `total = dispatch_cost × M + D`, with the dispatching cost of the instance file (300). `D` already
  includes the unit travel cost.
* **Gehring–Homberger (VRPTW):** the 18 instances with 200 customers and the 18 with 400 customers selected by Lei, Hao
  and Wu (2026), solved as VRPSPDTW instances without pickups. The objective is the total distance `D`, with no vehicle
  cost, and distances and travel times are Euclidean distances truncated to one decimal; `total = D`.

The instance files are not redistributed here. The WC and JD instances come from the public data of Liu et al. (2021),
available in the repository `senshineL/VRPenstein` on GitHub, and the Gehring–Homberger instances from the distribution
of SINTEF.

## Campaigns

Every campaign runs CoPTS-VRP (`algo = copts`) unless stated otherwise. A budget is the wall-clock time of a whole run.
Files named `<tag>_t<seconds>` hold the best solution of the same runs found before that time. A few campaign files also
hold runs of an earlier version of the same configuration; the article uses the rows whose `params` equal the
configuration it states.

**Results tables of the article.** The campaigns of the final configuration, listed in the protocol table of the article.

**Batched memetic organisation (BMA).** The campaigns with `algo = gma` run a batched memetic algorithm built on the
routing layer of CoPTS-VRP and run on the same GPU. Table S4 of the supplementary material reports `ablwc_bma` and
`abljd_bma` (the ablation protocols above, with route opening forbidden in its local search, as in MA-FIRD),
`ablwc_bmaopen` (the WC protocol with route opening allowed) and `bmajd3600` (JD 400_1 and 600_4, seeds 1-2, 3600 s,
compared with `jd7200_t3600`). `gma120_s1` (40 medium WC instances, 120 s, an earlier version) and `bmawc60` (the 56
medium WC instances, 60 s, seed 1, route opening forbidden) are not used in the article.

**Earlier configurations.** The campaigns `wcsmall10_30s`, `wc60_30s`, `wc180_30s_slow`, `wc120v2_s1`, `jd_v2`,

**Development runs.** The tags `wc120_s1`, `jd1200_s1`, `jdpilot`, `test_restart`, `test_fullrestart` and

## File formats

### `campaign_<tag>.csv`

| Column | Meaning |
|---|---|
| `tag` | Campaign name. |
| `algo` | `copts` (CoPTS-VRP) or `gma` (batched memetic baseline). |
| `instance`, `kind` | Instance name and benchmark (`WC` or `JD`). |
| `seed`, `time_budget` | Seed of the run and wall-clock budget in seconds. |
| `M`, `D`, `total` | Vehicles, distance (travel cost) and objective of the best solution of the run. |
| `bks_M`, `bks_D`, `bks_total` | Best-known solution used as reference (see *Reference values*). |
| `gap_pct` | `100 × (total − bks_total) / bks_total`. |
| `status` | `NEW_BEST` below the reference, `TIE` equal to it, `worse` above it; empty when the instance has no reference value. |
| `t_best` | Seconds from the start of the run to its best solution. |
| `epochs`, `iters` | Epochs and tabu iterations per trajectory performed in the run. |
| `params` | JSON with the parameters that differ from the defaults of the code. |
| `file` | Base name of the files of the run in `copts/` or `gma/`. |

### Solution files (`*.sol.txt`, `new_best/*.txt`)

The first line is `Solution: <vehicles> <distance> <total>`. Each following line is a route: the depot `0` followed by
the customers in visiting order, separated by commas. The return to the depot is implicit.

### Run files (`copts/*.json`, `gma/*.json`)

| Key | Meaning |
|---|---|
| `algo`, `instance`, `params` | Method, instance and the complete parameter set of the run. |
| `best_M`, `best_D`, `best_total`, `best_time` | Best solution of the run and the time at which it was found. |
| `elapsed`, `epochs`, `iterations` | Wall-clock time, number of epochs and iterations per trajectory. |
| `routes` | Routes of the best solution, as lists of customer ids. |
| `trace` | One record per epoch: time `t`, best solution so far (`best_M`, `best_D`), incumbent statistics, pool statistics and a `restart` marker when a restart happened. |

### `repair_diag.json`

For each seed, `alive` is the number of feasible local optima that lose their shortest route and `start_routes` their
route counts. For each repair variant, `variants[<name>]` lists the state after `k` iterations, with `k` in `ks`. The
`found_*` fields count the solutions whose best visited feasible solution is feasible (`found_feasible`), has one route
fewer than before the removal (`found_reduced`) or has at most 14 routes (`found14`). The other fields describe the
current solution after `k` iterations.

## Verification

Every solution in `new_best/` was re-evaluated with an independent double-precision CPU evaluator from the instance data,
with a tolerance of 1e-6 on every time window and load. The same evaluator reproduces the published solution files of
MA-FIRD, from which the reference values are taken.

## Reference values

The columns `bks_M`, `bks_D` and `bks_total` of the campaign files hold the best-known value of each instance at the
start of the study: the best over the published results of ALNS-PR, MATE, MATE* and MA-FIRD, as reported by Lei and Hao
(2025). This is the value of MA-FIRD on the 8 WC instances it improved and on the 20 JD instances, re-evaluated from its
published solution files. Those solution files are not included here.
